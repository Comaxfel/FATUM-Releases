# FATUM release workflow

Этот файл нужен как постоянная инструкция для будущих выпусков FATUM VTT, в том числе когда новый чат ChatGPT не помнит прошлый диалог.

## Текущая архитектура обновлений

FATUM использует публичный репозиторий `Comaxfel/FATUM-Releases` как stable-канал обновлений.

Клиентский обновлятор читает `latest.json` из ветки `main` и скачивает дельта-патч из `patches/`.

Пользовательские данные и пользовательские ресурсы должны сохраняться между обновлениями. Не заменять и не удалять `FATUM-data/`, `data/`, backups и пользовательские overrides. Пользовательские изображения/звуки/курсоры должны иметь приоритет через систему overrides.

## Цепочки обновлений и пропущенные версии

Постоянный updater, установленный начиная с FATUM 1.7.9, умеет проходить несколько дельта-патчей за один запуск `UPDATE_FATUM.cmd`. Например, при `latestVersion = 1.8.0` клиент 1.7.9 должен автоматически пройти `1.7.9 → 1.7.10 → 1.8.0`, если обе записи присутствуют в `packages`.

Поэтому `latest.json` — это не только описание последнего патча, а граф поддерживаемых переходов. При каждом новом релизе:

- не удалять старые рабочие записи `packages`, пока соответствующие исходные версии считаются поддерживаемыми;
- добавлять новый переход `предыдущая stable → новая stable`, а не заменять весь массив `packages` только новой записью;
- перед переключением `latestVersion` проверять, что от каждой поддерживаемой версии существует непрерывный путь до новой stable;
- отдельно тестировать как прямое обновление с предыдущей stable, так и хотя бы один сценарий с пропуском промежуточной версии;
- не допускать разрыва цепочки: если для промежуточной версии нет `from`-пакета, старый клиент остановится с ошибкой «нет подходящего дельта-патча».

Текущий updater выбирает следующий доступный пакет для своей текущей версии и повторяет обновление до `latestVersion` (с защитным пределом длины цепочки). Пользователю достаточно один раз запустить `UPDATE_FATUM.cmd`.

## Bootstrap 1.7.9

Первоначальные bootstrap 1.7.9 и r2 оказались недостаточно удобными для layout, где внешний каталог FATUM содержит вложенную папку `FATUM Desktop` с настоящим `FATUM.exe`: постоянный updater мог устанавливаться внутрь `FATUM Desktop`, поэтому пользователь не видел `UPDATE_FATUM.cmd` в основном внешнем каталоге.

Для распространения игрокам использовать **только** `FATUM-Updater-Bootstrap-v1.7.9-r3.zip`. R3 после перехода 1.7.8→1.7.9 явно создаёт `UPDATE_FATUM.cmd`, `RESTORE_FATUM.cmd`, `SAVE_MY_RESOURCES.cmd` в основном внешнем каталоге FATUM и одновременно устанавливает updater engine рядом с реальным `FATUM.exe`.

Если пользователь уже обновился до 1.7.9, но не видит `UPDATE_FATUM.cmd` в основном каталоге, не запускать патч 1.7.8→1.7.9 повторно. Использовать **`FATUM-Updater-Repair-v1.7.9-r2.zip`**. Repair r2 поддерживает как плоский layout с `FATUM.exe` в корне, так и вложенный `FATUM Desktop/FATUM.exe`.

Старые `FATUM-Updater-Bootstrap-v1.7.9.zip`, `...-r2.zip` и `FATUM-Updater-Repair-v1.7.9.zip` больше не распространять.

## Что делать при новом патче

1. Взять присланный пользователем архив как фактическую текущую базу FATUM. Не предполагать, что предыдущая локальная копия актуальнее.
2. Проверить текущую версию в `package.json`/служебных version-файлах и наличие updater-конфигурации.
3. Внести требуемые изменения поверх этой базы, не откатывая уже существующие механики.
4. Прогнать релевантные регрессионные тесты и общий smoke/regression pass.
5. Повысить номер версии.
6. Собрать полный архив новой версии для резервной/чистой установки.
7. Собрать дельта-патч `FATUM-update-X-to-Y.zip`, содержащий только изменяемые программные файлы и update-manifest. Патч не должен писать в пользовательские данные/overrides.
8. Посчитать SHA-256 и размер ZIP.
9. Пользователь вручную загружает бинарный ZIP в `patches/`, если GitHub-коннектор не поддерживает бинарную загрузку.
10. Проверить, что ZIP доступен публично по ожидаемому raw URL и что его имя, размер и хэш совпадают с подготовленными значениями.
11. Проверить непрерывный путь обновления от всех поддерживаемых старых версий до новой версии. Существующие нужные записи `packages` сохранять, новый переход добавлять к ним.
12. Только после успешной проверки обновить `latest.json`: `latestVersion`, `updatedAt`, добавить package `from`, `to`, raw URL, SHA-256 и размер. Публикация `latest.json` является финальным переключателем релиза, чтобы клиенты никогда не увидели ещё не загруженный патч.

## Что пользователь должен загрузить в GitHub

Для обычного нового релиза пользователю обычно нужно вручную загрузить только один бинарный файл:

`patches/FATUM-update-X-to-Y.zip`

`latest.json` можно обновлять через подключённый GitHub-коннектор ChatGPT после проверки загруженного ZIP. Полный архив новой версии не обязателен для автообновления; его можно хранить отдельно как резервный clean-install пакет.

## Правила совместимости

- Не заменять целые файлы из старой соседней ветки, если актуальная база содержит новые механики; делать diff/merge поверх присланной версии.
- Не считать одинаковый номер версии доказательством одинакового содержимого. Сначала сравнивать архивы/файлы.
- Не переносить условные пользовательские ресурсы обратно внутрь программных assets, если для них существует overrides.
- Любая миграция формата сохранений должна быть обратимо защищена backup-ом.
- Перед релизом обновлятор должен отклонять попытки патча писать в `data/`, `FATUM-data/` и другие защищённые пользовательские каталоги.
- Не публиковать `latestVersion`, для которой хотя бы у одной поддерживаемой версии отсутствует непрерывная цепочка `packages` до этой версии.

## Если пользователь прислал архив и сказал «выпусти новую версию»

Сначала прочитать этот файл из `Comaxfel/FATUM-Releases`, затем использовать присланный архив как source of truth и выпускать новую версию через описанный выше delta-update workflow.
